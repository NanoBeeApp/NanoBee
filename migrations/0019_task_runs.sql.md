# migrations/0019_task_runs.sql

## Purpose

Introduces the `task_runs` table that stores one execution-history row per
logical task run (success / failure / skipped). This powers the run-history
timeline in the task detail drawer and the plain-language failure explainer.

Key design decisions:

- **Status values**: `ok` | `failed` | `skipped` (not `success` to avoid an
  asymmetry between batch subtask status and task-run status at the DB level).
- **Granularity**: one row per logical execution for cron/condition tasks; one
  row per *chunk* for batch tasks (sub-task failures are tracked separately in
  `batch_subtasks.error_text`).
- **summary_text** ≤ 280 chars — human-readable one-liner shown in the UI
  timeline.
- **error_text** ≤ 1000 chars — generated by `failure-explainer.ts` (no LLM),
  never raw stack traces or secrets.
- **detail_json** — optional structured diagnostic context (metric value, retry
  count…); not exposed to the UI, used for debugging only.
- **Pruning**: `task-runs/repo.ts:createTaskRun` lazily deletes rows beyond
  `MAX_RUNS_PER_TASK = 200` per task after every insert, keeping the table
  bounded without a scheduled background job.
- **Indexes**: primary lookup is `(owner, task_id, started_at DESC)` to list
  recent runs for one task; secondary `(started_at DESC)` for age-based stats
  or a future global cleanup sweep.
