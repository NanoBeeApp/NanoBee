# 🎨 UI rules

> Split from CLAUDE.md on 2026-06-15. This is an inseparable part of the CLAUDE.md rules (loaded on demand to keep the always-on context small). Must be fully followed when relevant; violating it equals violating CLAUDE.md.

- **Every page must have a white background** (`var(--bg)` = `#ffffff`). Page-level containers (reading surfaces, task center, auth pages, chat, etc.) must never use gray fills like `var(--surface-2)` / `var(--surface-3)` as their background — those tokens are reserved for small inset elements (hover states, chips, code/spark blocks), not whole pages.
- **Always maximize the main content area — never let chrome crowd it out**. For every surface (page, dialog, modal, panel, drawer), the primary content is what the user came for; framing chrome (header bars, footer bars, toolbars, breadcrumbs, oversized titles/subtitles, nested cards) must stay minimal and must not eat vertical/horizontal space the content needs. Concretely: do not stack a full-width header bar *and* a full-width footer bar around a modal body — drop redundant titles (the dialog already has an `aria-label`/context), float the close affordance instead of giving it its own bar, and fold commit actions (Save/Cancel) into an existing column or a slim inline strip rather than a dedicated footer band. When a form/body is being clipped or scrolls awkwardly, first reclaim space from chrome before shrinking the content. This reinforces the global "maximize the main content area" rule.

- **🚫 Never casually add any UI element that floats over and occludes the canvas / primary content — show transient state IN PLACE instead.** The canvas (and any primary content surface: reading pane, board, editor, article) is what the user came for; do not drop floating overlays on top of it by default — status pills, progress/"loading…" banners, toasts, badges, watermarks, floating action buttons, hint bubbles, etc. Anything painted above the content steals attention and hides part of it.
  - **Progress / loading / empty state belongs in the content flow, not on top of it.** Show generation/loading where the content will appear — an in-place skeleton or inline indicator sized to mirror the real content (so there is no layout shift when it lands) — rather than a floating chrome element hovering over the surface. (This is why outline-generation shows a canvas skeleton, and the old floating "generating…" pill was removed.)
  - **A floating element is justified only when it is genuinely transient AND cannot live in the content** (e.g. a dismissible failure pill). Then keep it minimal, pin it to an edge/corner out of the content's way, auto-dismiss it, and never let it cover what the user is reading or manipulating.
  - **Any `absolute`/`fixed` overlay must clear fixed sibling chrome** (e.g. the fixed sidebar rail): offset it by that chrome's width so it is neither hidden behind it nor obstructing the content.
  - **Before adding anything on top of the canvas, justify why it cannot be shown in place.** If it can be shown in place, it must be. "It was easy to float it" is not a justification.
